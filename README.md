# GardenMDM

Локальная однопользовательская MDM-система: контрагенты, банковские счета и строительные проекты. Интерфейс на русском языке. Express 5 + TypeScript + PostgreSQL 15, HTML/JavaScript + локальная сборка Tailwind CSS, Nginx. Node.js 24 LTS используется внутри Docker; версия Node.js на хосте не влияет на запуск.

## Быстрый запуск

Нужны Docker Engine и Docker Compose с поддержкой `depends_on.condition` и `--wait`. Node.js, npm и PostgreSQL на хосте не нужны.

```bash
git clone <адрес-вашего-репозитория> GardenMDM
cd GardenMDM
docker compose up --build -d --wait
```

Приложение: http://localhost/ на компьютере, где запущен Docker. Первый запуск загружает образы и зависимости из интернета. После сборки интерфейс не обращается к CDN, шрифтам или другим внешним ресурсам.

Без `.env` работают демонстрационные параметры Compose. Для собственной установки перед первым запуском скопируйте `.env.example` в `.env` и задайте пароль PostgreSQL. `.env` не включается в Git. Изменение пароля в `.env` после создания тома само по себе не меняет пароль существующей роли PostgreSQL.

## Доступ к установленному серверу

Проект установлен в `/home/user/GardenMDM` на Debian `172.16.12.163`. Приложение слушает **только 127.0.0.1:80 сервера**. Чтобы открыть его на Windows, запустите в PowerShell:

```powershell
ssh -N -L 18080:127.0.0.1:80 -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 -o IdentitiesOnly=yes -i "$env:USERPROFILE\.ssh\gardenmdm_temp" user@172.16.12.163
```

Оставьте окно открытым и перейдите на http://127.0.0.1:18080/. Остановка туннеля — Ctrl+C. Если локальный порт занят уже работающим туннелем, используйте его или выберите другой свободный порт, например `18081`.

Приложение не содержит авторизации и предназначено для одного доверенного пользователя. Не публикуйте его в общей сети до добавления авторизации, ролей и HTTPS. В Compose есть `BIND_ADDRESS` и `HTTP_PORT`, но изменение адреса публикации — отдельное решение администратора. Backend и PostgreSQL не публикуют порты хоста: другие приложения на сервере, включая сервис на порту 3000, не затрагиваются.

## Сущности и правила

### Контрагенты

- UUID, наименование, ИНН, КПП, юридический адрес, статус, даты создания и изменения.
- ИНН: 10 или 12 цифр с проверкой контрольных разрядов в API, уникальный, неизменяемый.
- Для ИНН из 10 цифр нужен КПП из 9 цифр; для 12 цифр КПП отсутствует.
- Новый контрагент всегда находится на проверке и создаётся вместе со счетами в одной транзакции.
- Физического удаления контрагентов нет; используется архивирование.

Переходы статусов:

| Исходный статус | Разрешённые следующие |
| --- | --- |
| PENDING_REVIEW | ACTIVE, REJECTED, ARCHIVED |
| REJECTED | PENDING_REVIEW, ARCHIVED |
| ACTIVE | ARCHIVED |
| ARCHIVED | PENDING_REVIEW |

Повтор текущего статуса допустим. `MERGED` зарезервирован: отображается и фильтруется, но назначение и объединение записей не реализованы.

### Банковские счета

- Один или несколько счетов у каждого контрагента, ровно один основной.
- БИК — 9 цифр, счёт и заполненный корреспондентский счёт — 20 цифр. Реквизиты хранятся строками.
- Валюты: RUB, USD, EUR, CNY. Банки в этой версии российские.
- Один и тот же БИК + номер счёта нельзя повторить внутри контрагента.
- Последний счёт удалить нельзя. При удалении основного нужно выбрать другой основным.
- Отложенные constraint-триггеры проверяют весь набор счетов в момент фиксации транзакции. Частичный уникальный индекс защищает от нескольких основных счетов; блокировки строки контрагента сериализуют изменения.
- Контрольный ключ счёта, принадлежность счёта организации и существование банка во внешнем справочнике не проверяются.

### Строительные проекты

- UUID, название, адрес, город, начало и окончание строительства, ТЭП.
- Заказчик и Подрядчик обязательны; Посредник необязателен. Все роли ссылаются на справочник контрагентов.
- Можно назначать только активных контрагентов. Ранее назначенный участник сохраняется при последующем архивировании; проект можно редактировать, не меняя эту ссылку.
- Один контрагент может исполнять несколько ролей и участвовать в нескольких проектах.
- Окончание не раньше начала. Календарные даты не преобразуются через часовые пояса.
- ТЭП — массив показателей `name`, `value`, `unit`. Значения конечные и неотрицательные, названия уникальны без учёта регистра.

## Интерфейс

Две вкладки: «Контрагенты» и «Проекты». Поиск с задержкой 300 мс, фильтры, сортировка по заголовкам и страницы по 20 записей. Клик выбирает строку; двойной клик или Enter открывает карточку. Действия со статусами зависят от текущего состояния.

У контрагентов начальный фильтр — «На проверке». При редактировании ИНН недоступен. Для существующей записи реквизиты и банковские счета сохраняются отдельными действиями. Участники проектов выбираются через поиск активных контрагентов с серверной пагинацией. ТЭП редактируются строками без ручного JSON.

## Миграции и демонстрационные данные

SQL-схема: `database/migrations/001_schema.sql`. Перед открытием HTTP-порта backend применяет новые миграции в транзакции под advisory-блокировкой. История и SHA-256 хранятся в `schema_migrations`. Изменение уже применённой миграции останавливает запуск — изменения схемы оформляются новым файлом.

`database/seed.sql` создаёт 10 вымышленных контрагентов, 13 счетов и 5 проектов. ИНН имеют корректные контрольные разряды; реквизиты демонстрационные. Автозаполнение управляется `SEED_DEMO_DATA=true` (по умолчанию). Маркер `seed_runs` не допускает повторного заполнения после пользовательских изменений. Повторный запуск SQL не перезаписывает существующие записи.

Постоянные данные находятся в томе `gardenmdm_postgres_data`, а не в Git.

## Команды обслуживания

```bash
# Состояние и логи
docker compose ps
docker compose logs --tail=100 backend frontend

# Проверка готовности
curl -fsS http://127.0.0.1/api/health/ready

# Остановка с сохранением данных
docker compose stop

# Повторный запуск
docker compose up -d --wait

# Сборка обновлённого кода
docker compose up --build -d --wait

# Перезапуск
docker compose restart postgres backend frontend
```

### Резервное копирование

```bash
sh scripts/backup.sh
```

Файл в `backups/` — PostgreSQL custom-format dump. Каталог исключён из Git. Копируйте резервные копии на отдельное защищённое хранилище: копия на том же диске не защищает от его потери. Расписание резервного копирования не настроено.

### Восстановление

**Следующие команды заменяют текущие данные содержимым выбранной резервной копии.** Сначала сделайте свежую копию. Укажите реальный путь вместо `backups/имя.dump`:

```bash
docker compose stop backend frontend
docker compose exec -T postgres sh -c 'pg_restore --exit-on-error --single-transaction --clean --if-exists --no-owner --no-privileges -U "$POSTGRES_USER" -d "$POSTGRES_DB"' < backups/имя.dump
docker compose up -d --wait
```

### Полный сброс

**Команда ниже безвозвратно удаляет рабочую БД и все записи. Не нужна для обычного обновления.**

```bash
docker compose --profile test down --volumes
docker compose up --build -d --wait
```

## Проверки

```bash
sh scripts/test.sh
```

Тесты работают с отдельным сервисом `test-db`, временным хранилищем и БД `mdm_test`. Есть дополнительная защита от запуска тестов на другом имени БД. Рабочие данные не очищаются. Остановить тестовую БД после проверки:

```bash
docker compose --profile test stop test-db
```

Тестовый образ собирает TypeScript; frontend проходит проверку синтаксиса и сборку Tailwind. Интеграционные тесты проверяют создание записей, ИНН/КПП, откат транзакций, банковские ограничения и параллельные операции, статусы, связи проектов, даты/ТЭП, фильтры и единый формат ошибок. Браузерная проверка выполнена вручную средствами автоматизации; автоматических браузерных тестов нет.

Для автоматического запуска при push и pull request подготовлен пример [docs/github-actions.example.yml](docs/github-actions.example.yml). Он не активирован: существующий токен отправки не имеет права `workflow`. Чтобы включить GitHub Actions, разместите этот файл в `.github/workflows/ci.yml` через интерфейс GitHub или с учётными данными, разрешающими изменение workflow.

Подробный API: [docs/API.md](docs/API.md). Результат приёмки: [docs/ACCEPTANCE.md](docs/ACCEPTANCE.md).

## Ограничения версии

Нет многопользовательской авторизации, журнала аудита, объединения дублей, импорта/экспорта из интерфейса и внешних проверок реквизитов. Правила назначения участников и переходов статуса выполняются через API; прямые административные SQL-запросы должны учитывать эти правила. Ограничения внешних ключей, структуры ТЭП, дат и наличия счетов дополнительно действуют в БД.
