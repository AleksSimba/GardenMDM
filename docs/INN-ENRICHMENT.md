# Заполнение контрагентов по ИНН

Состояние на 21 октября 2026 года. Общий механизм реализован со сменным поставщиком данных. Реализован и проверен на контролируемых ответах адаптер DaData. Внешний поиск на рабочем сервере **выключен**, пока не выбраны поставщик и API-доступ. Покупки, регистрация аккаунтов и запросы к платным API не выполнялись.

У пользователя уже приобретены Контур.Фокус и Seldon.Pro. Само наличие пользовательского доступа не подтверждает состав доступных API; пользователь уточняет его у менеджеров. Адаптеры Контур.Фокуса и Seldon в текущую поставку не входят: для них нужны подтверждённый доступ и актуальная техническая документация. Общие формы, кеш, сохранение источника и создание контрагента не зависят от формата конкретного API.

## Что уточнить у менеджеров

1. Входит ли API в действующий договор и какой именно продукт/тариф приобретён?
2. Доступен ли поиск базовых реквизитов ЮЛ и ИП по ИНН? Какие поля возвращаются?
3. Как получить тестовые и рабочие реквизиты доступа, документацию и примеры ответов?
4. Каковы квоты, стоимость превышения, ограничения IP и требования к тестированию?
5. Допускается ли хранение полученных данных в собственной MDM и последующая загрузка списка ИНН?
6. Есть ли сведения о банковских счетах и как подтверждается их актуальность/принадлежность? Не считать их доступными без подтверждения состава API.

Ключи, пароли и cookies в чат и Git не передавать. Настройка доступа выполняется на сервере.

## Пользовательский сценарий

1. Открыть создание контрагента и ввести ИНН.
2. Нажать «Найти по ИНН». Поиск выполняется явно, а не при каждом нажатии клавиши.
3. Просмотреть найденные сведения, дату получения, актуальность и предупреждения.
4. Нажать «Заполнить реквизиты». Для замены уже введённых значений нужна отметка подтверждения.
5. Проверить заполненные поля, вручную добавить подтверждённый банковский счёт и сохранить.

Новая запись остаётся `PENDING_REVIEW`. Статус реестра и статус MDM независимы. Поиск не создаёт контрагента и не меняет существующие записи. Для уже имеющегося ИНН возвращается конфликт дубля. Изменение ИНН в форме сбрасывает выбранный результат.

Заполняются доступные наименование, КПП, адрес. Дополнительно сохраняются полученные полное/краткое названия, ОГРН/ОГРНИП, ОКПО, основной ОКВЭД, тип, регистрационная дата, статус реестра и руководитель/должность. Недоступные поля явно отмечаются. Длинное полное название сохраняется целиком в сведениях реестра; в основное поле предлагается краткое, если оно подходит по длине. Для ИП полного адреса может не быть.

DaData `findById/party` не предоставляет банковские счета контрагента. Их нельзя восстановить по названию банка или заменить фиктивными значениями. Инвариант «хотя бы один счёт и ровно один основной» сохранён.

## Реализация

- `PartyProvider` — интерфейс адаптера; DaData — текущая реализация. Клиент получает единый нормализованный формат.
- Только backend отправляет запрос на фиксированный официальный HTTPS-адрес. Ключ не возвращается браузеру, не передаётся в URL и не сохраняется в ответах/кеше.
- Проверяются формат и контрольные разряды ИНН. Запрашивается головная организация или ИП; результаты другого ИНН и филиалы не применяются. Неоднозначный ответ требует ручной проверки.
- Таймаут — 7 секунд; максимум ответа — 1 МиБ; автоматических повторов нет.
- Положительные ответы кешируются в PostgreSQL на 24 часа. Ошибки и отсутствие результата не кешируются. Одновременные одинаковые запросы объединяются.
- В одном процессе backend допускается не более 30 новых внешних запросов в минуту и 3 одновременно. Кеш не расходует внешнюю квоту. При многопроцессном развёртывании нужен общий ограничитель.
- Для сохранения клиент передаёт `lookup_id`. Backend сам берёт сведения из своего кеша, проверяет срок и совпадение ИНН. Подмена `registry_snapshot` клиентом запрещена.
- Снимок источника хранится в `contractors.registry_snapshot`. Ручные изменения реквизитов допустимы; в карточке отмечается отличие от исходного результата.
- Миграция `002_inn_enrichment.sql` добавляет снимок и таблицу кеша без изменения существующих контрагентов и счетов.

## Подключение DaData, если будет выбран этот источник

1. Зарегистрироваться на [dadata.ru](https://dadata.ru/), подтвердить почту и получить **API-ключ**, а не Secret key.
2. На сервере выполнить:

```bash
cd /home/user/GardenMDM
python3 scripts/configure-dadata.py
```

Ключ вводится скрыто. Скрипт сохраняет `DADATA_API_KEY` и `INN_LOOKUP_PROVIDER=dadata` в локальном `.env`, сохраняя остальные параметры, и пересоздаёт backend. `.env` исключён из Git. Без выбора поставщика используется `INN_LOOKUP_PROVIDER=none`; ручное создание доступно.

Проверка состояния без раскрытия ключа:

```bash
curl -fsS http://127.0.0.1/api/integrations/inn/status
```

Только после добавления рабочего/тестового ключа можно подтвердить фактический ответ внешнего сервиса. Успешные ответы без ключа не имитируются в рабочем приложении.

## Подготовка будущего импорта

Список ИНН сам по себе недостаточен для создания полноценных записей с обязательными счетами. Предлагаемый будущий процесс: проверка файла и дублей → получение реквизитов выбранным API → предварительный отчёт → дополнение и проверка банковских счетов → подтверждение импорта. Записи без обязательных данных должны оставаться в отдельной подготовительной выборке, а не попадать в справочник с фиктивными реквизитами. Массовый импорт пока не реализован; пользователь предоставит данные позже.
